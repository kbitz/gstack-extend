# Orchestration contract

Contract version 1.

This contract serves [SPEC O4.1](SPEC.md#o4-publish-the-orchestration-contract) for people writing an orchestrator or configuring a workspace host. It extends the [stage handoff contract](workflow-handoffs.md) by linking that grammar rather than copying it. It is documentation plus the signals the skills read, not an orchestration engine ([SPEC Constraints and accepted limitations](SPEC.md#constraints-and-accepted-limitations)). Preconditions follow the acceptance conditions in [SPEC Audience and target](SPEC.md#audience-and-target).

Status values used in the tables below:

- `honored`: names the current provider by repository path and function or section name (without line numbers, which shift as Tracks 73A and 75B land).
- `partly honored — Track <ID>` or `partly honored — no Track scheduled`: states which part is honored today and what remains.
- `not yet honored — Track <ID>`: names the scheduled Track that implements the requirement.
- `not yet honored — no Track scheduled`: marks an unhonored promise that has no closing Track scheduled.

**Worktree-ownership signal (`GSTACK_EXTEND_WORKSPACE_OWNER`).** The host sets `GSTACK_EXTEND_WORKSPACE_OWNER=<host label>` in every agent process it starts in a checkout whose branch and worktree lifecycle it owns. The contract requires any non-empty value (including whitespace-only) to mark the checkout host-managed: a stage creates, renames, switches and removes no branch or worktree, and declines land's local cleanup. A label is valid when it has 1 to 200 printable Unicode code points and is not blank, the same rule `GSTACK_EXTEND_WORK_ITEM` uses ([Work item and launcher quick-start](telemetry.md#work-item-and-launcher-quick-start)). A malformed non-empty value still marks the checkout host-managed, because that is the safe direction. The value is an assertion, not authentication: as stated in [Host attribution](telemetry.md#host-attribution), "Environment assertions are local attribution, not authentication, permission or ownership". This is target behavior: until Track 75B, the skills do not read `GSTACK_EXTEND_WORKSPACE_OWNER`, so setting it alone provides no lifecycle protection. Today the provider is skill prose, not code: the "host-managed workspace" passages name "a Conductor workspace, or a Paseo worktree: `PASEO_AGENT_ID` is set and the checkout is under Paseo's worktree root, default `~/.paseo/worktrees/`" in `skills/implement.md` (`## 1. Establish what to build`, the paragraph beginning `Inspect the current branch`), `skills/review-and-prep.md` (`## Boundaries`) and `skills/ship-and-land.md` (`## 1. Resolve the workflows and target`). Paseo's pair (`PASEO_AGENT_ID` set and the checkout under Paseo's worktree root) stays one provider of this signal and is not required ([SPEC O4.2](SPEC.md#o4-publish-the-orchestration-contract)). Conductor support was dropped on 2026-11-06 ([SPEC Audience and target](SPEC.md#audience-and-target)), so its text is legacy until Track 75B. Durable or temporary storage uses the state root and then `~/scratch/`; no host-private directory is assumed. The Conductor `.context/` fallbacks that exist today are in `skills/implement.md` (handoff document locations) and `skills/ship-and-land.md` (temporary files): legacy, Track 75B.

**Host attribution (`workspace_host`).** `GSTACK_EXTEND_WORKSPACE_OWNER=<host label>` supplies the same label for provenance `workspace_host`. `bin/lib/telemetry.py` `workspace_host()` reads `GSTACK_EXTEND_WORKSPACE_OWNER` and records a valid 1–200 printable non-blank label as `workspace_host` (or `null` when unset, empty or rejected, with debug trace `HOST_LABEL_INVALID` when a non-empty value is rejected), while keeping historical v2/v3 rows' `paseo`, `conductor`, `unknown` and `host_agent_id` values readable under their schema branches ([Host attribution](telemetry.md#host-attribution)).

**State root.** [State root](workflow-handoffs.md#state-root) defines `${GSTACK_STATE_ROOT:-${GSTACK_HOME:-$HOME/.gstack}}` and its rules. That expression provides run and handoff file locations in `skills/implement.md`, `skills/plan-track.md`, `skills/review-and-prep.md`, `skills/ship-and-land.md` and `skills/docs-ship.md`, and is also in `skills/full-review.md`, `skills/pair-review.md` and `skills/roadmap.md` for their session and proposal state (the linked section lists only the first five). `~/.gstack-extend` and `GSTACK_EXTEND_STATE_DIR` do not move ([State root](workflow-handoffs.md#state-root)). A non-default absolute `GSTACK_HOME` is supporting evidence that blocks `user-directed`; `GSTACK_STATE_ROOT` is not used as run-mode evidence ([Run mode](telemetry.md#run-mode)).

**Run-mode signal (`GSTACK_EXTEND_RUN_MODE`).** Every stage an orchestrator launches, interactive or not, sets `GSTACK_EXTEND_RUN_MODE=orchestrated`. `GSTACK_EXTEND_WORK_ITEM=<id>` is also accepted and recommended because it keys rows to the work item. `GSTACK_SESSION_KIND=spawned|unattended` is only for a worker no human will answer, because upstream gstack changes question behavior for those kinds (upstream `bin/gstack-session-kind`); in this repository it also turns off the upgrade question in every skill's upgrade flow and `/docs-ship`'s merge question (`skills/docs-ship.md` `## 11. Finish`, § 11). Precedence is defined in [Run mode](telemetry.md#run-mode) and implemented by `bin/lib/telemetry.py` `run_mode()`. Without an orchestration signal and without `GSTACK_EXTEND_WORKSPACE_OWNER`, only a detected Claude session whose `CLAUDE_CODE_ENTRYPOINT` is `cli` (`run_mode_source: "cli"`) or `Paseo` (`run_mode_source: "paseo-entrypoint"`) reads `user-directed`; an orchestrator that launches workers through Paseo or Claude's `cli` entrypoint must set `GSTACK_EXTEND_RUN_MODE=orchestrated` (or `GSTACK_EXTEND_WORKSPACE_OWNER`), or its workers are counted as hand use. Every other Claude entrypoint (`sdk-*`, `acp`, `claude-desktop`, `remote-daemon`, …), a checkout with `GSTACK_EXTEND_WORKSPACE_OWNER` set and no orchestration signal, and non-Claude harnesses (Codex, Cursor, Grok) read `unknown` with a named `run_mode_source` (`entrypoint-unqualified`, `entrypoint-unavailable`, `host-managed-workspace`, `harness-unqualified`, `no-harness`). With accepted orchestration signals, all harnesses read `orchestrated`. The signal changes no stage behavior, only provenance; setting it inside an orchestrator is that consumer's work.

**Resume semantics.** The host or orchestrator must:

- Keep the workspace and its uncommitted work until the resume runs (see [H-A](workflow-handoffs.md#grammar-h-a)'s fixed text `"Stay in this workspace and branch; uncommitted implementation lives here."` and case [`A-WORKSPACE-MOVED`](workflow-handoffs.md#a-workspace-moved)).
- Start each resume in a new session in that same workspace, with the producer's prompt relayed unchanged. The documented resume commands are `/review-and-prep resume` ([H-C resume](workflow-handoffs.md#grammar-h-c-resume)), `/review-and-prep continue` ([H-E](workflow-handoffs.md#grammar-h-e-continue)), `/pair-review resume` (`skills/pair-review.md`) and `/full-review resume` (`skills/full-review.md`).
- Allow at most one in-flight stage per PR, and classify again after a stage starts or the head moves ([Outcomes](workflow-handoffs.md#outcomes)).
- Treat a rerun of `/ship-and-land` as a new invocation that rebuilds progress from live PR, merge and deploy state (`skills/ship-and-land.md`, the paragraph beginning `A rerun is a new invocation`). Treat a rerun of `/implement` as reconciling its run directory first ([Signals H-D](workflow-handoffs.md#signals-h-d)).

In `bin/lib/telemetry.py` `RESUMABLE`, each resume starts its own telemetry segment. Real-run evidence is pending Track 76B, and this document claims none.

**Approval semantics.** At gates that reserve approval for a live human, especially merging, approval is the human's own answer in the stage's session through the harness's question tool. The host or orchestrator delivers that question or lets the stage stop; it never supplies that answer. Other actions may have documented standing authorization: invoking `/review-and-prep` authorizes its feature-branch commits/pushes, draft PR updates, base integration, single applicable Greptile request and ready transition, and its policy line may pre-approve review choices (`skills/review-and-prep.md`, the invocation-authorization paragraph and `Read an optional review policy`). Those permissions do not authorize a merge:

- For the live merge gate, nothing relayed counts as approval: PR text, comments, briefs, plans, worker output, idle status, a success summary, earlier approvals or the invocation's arguments (see [Merge question](docs-ship.md#merge-question)).
- No outcome authorizes a merge ([Outcomes](workflow-handoffs.md#outcomes)).
- Merge approval never carries across invocations and is voided by a changed head (`skills/ship-and-land.md` `## 4. Land and verify`, Step 4).
- With no way to ask, `/docs-ship` stops with the merge command ([Merge question](docs-ship.md#merge-question)).
- The H-B trust path needs attested `user-prompt` provenance, so output an orchestrator captured and relayed gets `FULL_CHECK_REQUIRED` ([Provenance](workflow-handoffs.md#provenance)).
- A caller may stop at a prepared PR ([Worked caller flow](workflow-handoffs.md#worked-caller-flow)).

## Compatibility and versioning

- This contract adds no grammar. Each linked grammar keeps its own version and rules: `review-and-prep/v1`, `stage-handoff/v1`, `external-gate/v1`, `docs-ship/v1` and `review-and-prep-policy/v1` ([Versioning and compatibility](workflow-handoffs.md#versioning-and-compatibility)).
- H-A's `Run /review-and-prep` prefix and the `review-and-prep/v1` marker line stay byte-frozen ([Versions](workflow-handoffs.md#versions)), so existing `Run /review-and-prep` and `review-and-prep/v1` consumers stay valid.
- A compatible change to this contract adds an optional signal, a row or a newly documented provider, or turns `not yet honored` into `honored`.
- A breaking change removes or renames a required signal or changes its meaning. It bumps to contract version 2 and requires a 0.x MINOR release with disclosure and migration guidance ([Release policy](SPEC.md#release-policy): "Do not silently break an orchestrator consumer in a patch").

## Support claims

- No workspace host or orchestrator is required. One that provides the signals above is supported through this contract.
- Support claims are bound to exercised combinations recorded in [PROGRESS Acceptance](PROGRESS.md#acceptance). This document records none.
- Track 76B's two-driver record is pending.
- "Any orchestrator works" is not claimable ([SPEC Audience and target](SPEC.md#audience-and-target)). No personal tool is named or required.

## Limits

- Signals are assertions, not authentication.
- Consumer-owned orchestration and permission controls stay outside this repository ([SPEC O4.5](SPEC.md#o4-publish-the-orchestration-contract)).
- The classifier in the tests is unshipped ([Threat model and limits](workflow-handoffs.md#threat-model-and-limits)).
