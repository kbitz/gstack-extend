# Compatibility and recovery catalog

This catalog serves [SPEC O5.1](SPEC.md#o5-make-a-stable-release-promise-that-the-tooling-can-keep): it lists the promised compatibility surfaces (including the [orchestration contract](orchestration-contract.md)), experimental exclusions, private internals, retired surfaces, support conditions and recovery links in one place.

## Purpose and boundary

This document indexes promises already made in the linked specifications. It adds no new promise, changes no version rule and is not acceptance evidence. [SPEC Release policy](SPEC.md#release-policy) owns the release and compatibility rules, [PROGRESS Acceptance](PROGRESS.md#acceptance) owns achieved checkpoint evidence, and each linked contract keeps its own version number and evolution rules.

## How to read it

Every surface falls into one of three classes from [SPEC Release policy](SPEC.md#release-policy):

- **Stable:** covered by a [SPEC Release policy](SPEC.md#release-policy) stable-surface category ("documented CLI arguments/exit and JSON semantics, skill names and required inputs, the orchestration contract and versioned handoff and provenance schemas, installation ownership, supported configuration and approval/hold semantics") and promised by its own document.
- **Experimental:** its own document labels it experimental or shadow-only ([SPEC Non-goals and later work](SPEC.md#non-goals-and-later-work)); it keeps its explicit schema-version rules and does not gate 1.0.
- **Private:** internal stores, state files, helper commands and code modules whose documents call them private or internal.

In the **Pinned by** column below, a named test suite is automated fixture or contract evidence only. Installed operating-system, workspace-host and agent-harness qualification is **qualification unknown** unless [PROGRESS Acceptance](PROGRESS.md#acceptance) records an owner-accepted checkpoint for that combination. A documented surface whose own document assigns no stability label stays listed with **qualification unknown** and is not promoted here. The `Stable` / `New` / `Beta` column in [README Skills](../README.md#skills) describes day-to-day field maturity, not a compatibility tier.

## Version and compatibility rules

- **Release version format:** `MAJOR.MINOR.PATCH` (three-part, no prefixes or suffixes) from the first release cut from a base containing the transition policy ([Version numbers](installation.md#version-numbers), [`CLAUDE.md`](../CLAUDE.md#versioning)). Historical four-part tags and records stay intact and compare with padded numeric equality (`0.47.0 == 0.47.0.0`). Consumer projects keep their own version schemes and `init` defaults.
- **0.x release increments:** compatible additions use `0.x` MINOR; fixes and released documentation use PATCH after cutover ([SPEC Release policy](SPEC.md#release-policy)). Incompatible public changes require an explicit `0.x` MINOR release, release-note disclosure and migration or recovery guidance. Do not silently break an orchestrator consumer in a patch.
- **1.0+ release increments:** breaking stable-interface changes use MAJOR, compatible additions MINOR, and fixes or documentation-only releases PATCH ([SPEC Release policy](SPEC.md#release-policy)).
- **Independent surface versions:** a package release alone does not bump a schema or grammar version. Handoff and policy tokens follow [Versioning and compatibility](workflow-handoffs.md#versioning-and-compatibility), the orchestration contract follows [Compatibility and versioning](orchestration-contract.md#compatibility-and-versioning), telemetry schemas follow [Telemetry versions](telemetry.md#versions) ("A gstack-extend release alone does not change `schema_version`"), and quota JSON follows its `v` rule in [Consumer contract](quota-ledger.md#consumer-contract).

## Checked example: stage-runs

[`docs/stage-runs.schema.json`](stage-runs.schema.json) accepts `schema_version` 1 through 4, and the current writer (`bin/lib/telemetry.py` `finish()`) emits `4` ([Versions](telemetry.md#versions); [CHANGELOG](../CHANGELOG.md) `0.77.0`), writing to per-host `analytics/stage-runs/*.jsonl` while readers scan both the legacy `analytics/stage-runs.jsonl` and per-host files ([Per-host files and migration](telemetry.md#per-host-files)).

Track 28A verified stage-runs v2 three-part producer versions (`0.47.0` and `1.0.0` accepted; `0.47` and `0.47.0.0.0` rejected) against the JSON schema, the executable validator (`gstack-extend-telemetry validate-stage-runs`, [Schema validation](telemetry.md#schema-validation)) and the quota ledger's attribution projection ([Boundaries and stable surface](acceptance/release-compatibility.md#boundaries-and-stable-surface)). `tests/telemetry-contract.test.ts` reads v1–v4 rows through `gstack-extend quota runs` and locks schema validation across those versions. Recovery follows the reader-first migration and rollback rule in [Producer version](telemetry.md#producer-version) and [Version numbers](installation.md#version-numbers): upgrade readers before writers, retain readers capable of every emitted schema version, and never rewrite existing JSONL rows on rollback. This is one checked example of a versioned provenance schema, not the whole compatibility catalog.

## Experimental exclusions

These surfaces remain explicitly excluded from 1.0 gates under [SPEC Non-goals and later work](SPEC.md#non-goals-and-later-work) and keep their own version rules:

- **Quota ledger (`gstack-extend quota`, `gstack-extend doctor quota`):** documented in [Quota ledger](quota-ledger.md). Every JSON response carries `v: 1` ([Consumer contract](quota-ledger.md#consumer-contract)), and that published data contract is preserved while capacity adapters remain `support: "experimental"` pending 24-hour coverage trials. Its SQLite store is private. Conductor's Cursor SDK store reader, `--conductor-store` flag and `--route conductor` value are removed; runs recorded earlier with route `conductor` and native Cursor SDK sources already in the store stay readable through unfiltered `quota runs` and `quota summary --by route` ([Runs and consumption](quota-ledger.md#runs-and-consumption)).
- **Merge gate (`bin/merge-gate`):** shadow-only advisory verdict CLI documented in [Merge gate](merge-gate.md). It never merges, pushes or updates refs; its JSON and text output (`v: 1`) follows [Versioning](merge-gate.md#versioning).
- **Review independence (`docs/designs/review-independence.md`):** design and evidence boundary only ([Review independence](designs/review-independence.md), [SPEC Supporting documents](SPEC.md#supporting-documents)); defines no empirical clearance and no release gate.
- Any other surface whose own document labels it experimental or shadow-only retains that label and is not promoted by this catalog.

## Private and internal surfaces

- **Quota SQLite database layout:** `quota/quota.sqlite3`, WAL/SHM files and `identity.key` under the state root ([Consumer contract](quota-ledger.md#consumer-contract): "The database layout is private").
- **`install-status` file and lock:** `${GSTACK_EXTEND_STATE_DIR:-$HOME/.gstack-extend}/install-status` and `install-status.lock` ([State recovery](installation.md#state-recovery): "a private data file").
- **`bin/outside-review`:** internal Claude Code review adapter called by `/review-and-prep` ([Invocation and scope](outside-review.md#invocation-and-scope): "Internal command").
- **`bin/review-delegate`:** internal specialist delegation runner called by `/review-and-prep` ([The command line](delegated-review.md#the-command-line): "internal to `/review-and-prep`").
- **Internal libraries and modules:** `bin/lib/**` and `src/**` (implementation modules behind the documented skills and `bin/` entry points, not a standalone library interface).
- **Test-only handoff classifier:** the reference classifier in `tests/handoff-contract.test.ts` ([Threat model and limits](workflow-handoffs.md#threat-model-and-limits): "the classifier in the tests is not shipped").

## Retired surfaces

- **Conductor support:** dropped on 2026-11-06 ([SPEC Audience and target](SPEC.md#audience-and-target)). Host-specific skill branches were removed in Track 76A (`0.84.0`), telemetry's `CONDUCTOR_SESSION_ID` marker and Conductor Cursor-store reader were removed in `0.77.0` ([Historical route caveat](telemetry.md#cursor-sdk-historical-route)), and the quota ledger's `--conductor-store` option, `conductor` `--route` value and Cursor SDK store reader were removed in Track 77A ([Consumer contract](quota-ledger.md#consumer-contract)). Historical rows naming `conductor` remain readable in stage-runs v1–v3 ([Versions](telemetry.md#versions)) and in unfiltered `quota runs` and `quota summary --by route` ([Runs and consumption](quota-ledger.md#runs-and-consumption)).
- **`/autoplan-lean` and `bin/autoplan-lean`:** retired in `0.72.0` ([CHANGELOG](../CHANGELOG.md)); replaced by `/plan-track` and upstream `/autoplan`.

## Support conditions

- **Runtime prerequisites:** Git repositories, GitHub PRs through authenticated `gh`, Bun (1.3.3+ for the commands listed in [README Installation](../README.md#installation)), installed upstream gstack, existing authorized agent accounts, and `setup` hosts Claude Code, Codex, Cursor and OpenCode ([SPEC Audience and target](SPEC.md#audience-and-target), [Installation](installation.md#installation)).
- **Workspace hosts and orchestrators:** none is required. Any host or orchestrator that supplies the signals in the [orchestration contract](orchestration-contract.md) is supported through that contract ([SPEC Audience and target](SPEC.md#audience-and-target)).
- **Exercised combinations:** support claims cover only the combinations recorded in [PROGRESS Acceptance](PROGRESS.md#acceptance). Today that table records **O2 (planning)** on **macOS / Paseo / Codex** (2026-10-23, [`docs/acceptance/planning.md`](acceptance/planning.md)); all other outcomes (O1, O3–O6) and all other operating-system, host and harness combinations are **qualification unknown**.
- **Upstream gstack qualification:** isolated candidate probes for `gstack-version-bump classify` and `gstack-next-version` against upstream gstack `1.91.185.0`, plus inspected review-adapter revisions, are recorded in [Release compatibility qualification](acceptance/release-compatibility.md) and [Inspected revisions](upstream-check.md#inspected-revisions).
