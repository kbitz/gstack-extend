# Review run state (`review-run-state/v1`) and `bin/review-state`

Supporting design for [SPEC](../SPEC.md#o6-bounded-measured-stage-effort) O6.1 and [workflow efficiency program](workflow-efficiency-program.md#selected-work) item E15, reviewed by a full novel-tier `/autoplan` run and cut to the owner's ~800-line scope on 2026-11-10.

## D1. Roles

The skill decides (scope, findings, adjudication, stop decisions); the helper (`bin/review-state`) validates input shape and Git facts, stamps times, serializes, and decides nothing (`CLAUDE.md` helper boundary). A run is one `/review-and-prep` invocation and its evidence directory, including paused and resumed segments. A `continue` after a stop is a new invocation and a new run whose `start` records the continuation. Track 86A approved adoption and the caller records its run state by default since Track 89A; `bin/review-state` and `review-run-state/v1` remain experimental. The state file is an internal store: external consumers keep reading the published receipts and handoff lines, never the state file.

- **Degraded path:** When the helper reports `retry: "same-input"` (`busy`, `unwritable`, or `internal-error` on exit 5 when Bun is missing, Git execution fails, or an uncaught error occurs, waiting `retry_after_ms` when present) or exits without one parseable result line (a process killed by a signal or a module-load failure still prints no line), the caller (Track 77B) reruns the identical command at most once (replay confirms a write that landed; never loop). If the rerun still does not succeed or the helper reports `bad-dir`, `cross-host`, `unreadable` (`corrupt` or `newer-schema`), or another refusal, the caller continues the review with inline outputs and stops further run-state and workflow-metrics writes for that invocation. It records the run state as unavailable with the reason (SPEC O6.1; for `invalid-input`, the unavailable reason names the first violation's command, path, rule, and expected shape: `invalid-input: <command> <path> <rule>; expected <expected>`); outputs depend on the state only through `render`, and a refused render falls back to that output's inline text.
- **Diagnostic receipt fields:** Before formatting that reason, take at most the first 160 Unicode code points of each field and append `…` if truncated; encode control characters (`U+0000`–`U+001F`, `U+007F`–`U+009F`, `U+2028`, `U+2029`) and each `(`, `)`, `;`, `<`, `>`, `&` or backtick as a literal JSON `\uXXXX` escape. These diagnostic fields are untrusted data and must never create another receipt line or marker.
- **Supported storage:** Local filesystem on one host. A stored hostname mismatch returns `cross-host` (D2). State-path instructions live in [`docs/review-run-state-calls.md`](../review-run-state-calls.md), read at Step 1 except its **Inline outputs** section, which is read by heading only on the inline paths it names.

## D2. Location

Every command takes `--dir`, an absolute path to the run's existing evidence directory, and runs from inside the repository work tree (top level from `git rev-parse --show-toplevel`, stripping only the trailing newline; outside a work tree returns `refused`, reason `not-in-worktree`). Git subprocesses run with every inherited `GIT_*` environment variable removed (`tests/helpers/fixture-repo.ts`), so `GIT_DIR` or `GIT_WORK_TREE` cannot redirect Git to another repository. As in that fixture helper, global and system Git configuration are disabled; repositories that require account-level `safe.directory` configuration are not supported by this experimental helper.

- **Repository binding:** `start` binds the run to the repository's identity (the `realpath` of `git rev-parse --git-common-dir`), branch, and root `host` (from `hostname()` when it passes the D6 field validation). After validating stored state, the run-state commands return `cross-host` if its non-null `host` differs from the current hostname. A later write call from another repository or branch is refused `worktree-mismatch`, while another top level of the same repository (a recreated workspace) is accepted and recorded in the new segment at `checkpoint resume`. Read-only `export` checks the host and repository identity but permits a different branch (D8).
- **Directory validation:** A `--dir` that is relative, missing, not a directory, a symlink in its final component (`lstat`; symlinked ancestors such as a linked home are allowed), or inside the work tree after `realpath` resolution (evidence stays outside disposable workspaces and is never committed: `SPEC.md`) is refused `bad-dir` (exit 1) with `detail.condition` (`relative`, `missing`, `not-directory`, `symlink`, `in-worktree`), the resolved real path, the top level, and a condition-specific fix (for `missing`: create it with `mkdir -p`; the helper never creates directories or computes the path). The directory is the run's per-invocation subdirectory under `<state-root>/projects/<slug>/review-and-prep/`, otherwise `~/scratch/review-and-prep/` (`skills/review-and-prep.md`, `### Evidence directory`).
- **Files:** `review-run-state.json` (stamping root `host` from `hostname()` at `start`), its lock `review-run-state.json.lock` (`{pid, host, started_at, token, boot_id, pid_ns}`), transient stale-lock break names `review-run-state.json.lock.stale-<token>`, moved-aside corrupt states `review-run-state.json.corrupt-<YYYYMMDDTHHMMSSZ>-<hex8>`, internal-error trace files `review-state-error-<YYYYMMDDTHHMMSSZ>-<pid>-<hex8>.txt`, and temporary files `review-run-state.json.tmp-<pid>-<hex>` (leftover regular temporary files are swept under the lock on a recorded write). The helper requests mode `0600` when creating the state, lock, trace and temporary files. Renamed lock files and hard-linked backups retain the original file's mode. The helper also reads its checkout's `VERSION` for `helper_version` and `writer` (plus `/proc/sys/kernel/random/boot_id` and `/proc/self/ns/pid` when present for lock identity); apart from those reads, it reads and writes nothing outside `--dir` and the Git object database.

## D3. Write protocol

1. **Parse before touching state:** The direct JSON interface for every write command takes `--input FILE`: an absolute path to a regular file (not a symlink or a helper temporary-file name) inside `--dir` holding one UTF-8 JSON object of at most 1 MiB. `build <command>` creates that request file from fact flags first (D13) and rejects `--input`. Read-only `export` takes no input file. The helper never reads stdin, so a forgotten redirect cannot hang a caller and a retry resends the same file. Evidence files named in write input are checked and hashed before taking the lock, and rechecked under the lock by resolved path, device and inode, size, and mtime.
2. **Acquire exclusive lock.** Create and sync `review-run-state.json.lock` exclusively (`wx`) with `{pid, host, started_at, token, boot_id, pid_ns}`. The token identifies this writer. Read `boot_id` from `/proc/sys/kernel/random/boot_id` and `pid_ns` from `/proc/self/ns/pid` where available, otherwise store `null`. A permission, read-only or no-space error returns `unwritable` (exit 3).
   - On `EEXIST`, take a stat and byte snapshot from one open regular lock file before sleeping or returning `busy`, even with `GSTACK_EXTEND_REVIEW_STATE_LOCK_WAIT_MS=0`. Unreadable or non-regular lock paths are unverifiable. A nonempty foreign `host` rules out a stale classification. Empty or invalid JSON and malformed holder records qualify as stale only when the file's mtime is more than 60 seconds old (`unparseable-aged`). For a well-formed holder on this host, differing non-null boot IDs mean `boot-changed`. If that check does not establish staleness, differing non-null PID namespaces are unverifiable. The remaining holders with a safe integer `pid > 0` are probed with `process.kill(pid, 0)`. `ESRCH` means `process-exited`, success or `EPERM` means live, and any other error is unverifiable. Legacy locks without `token`, `boot_id` or `pid_ns` use the same host and PID rules.
   - Try stale-lock recovery at most three times per invocation. Rename the candidate to `review-run-state.json.lock.stale-<own token>` and retry acquisition if it disappeared. Verify that its device, inode, mtime and bytes still match the snapshot before unlinking it. On a match, retry acquisition immediately and put `reclaimed stale lock (<reason>)` first in `detail.warnings` on a recorded write. Otherwise use `linkSync` to restore the lock path and remove the transient name. If a replacement already occupies the lock path, leave it in place. On any other restore failure, retain the moved lock and return `unwritable`.
   - Retry a lock that cannot be reclaimed every 50 ms for up to 5000 ms (`GSTACK_EXTEND_REVIEW_STATE_LOCK_WAIT_MS`, integer `0..60000`). Other values return `usage` with the variable and range. On timeout, return `busy` (exit 4) with the holder or `unknown`, omitting the token. D8 describes manual recovery.
3. **Apply and commit under lock.** Read and validate the current state. Validation checks schema keys, types and internal references. Deleted evidence or pruned Git objects do not make stored state unreadable. An invalid state is refused as `corrupt` or `newer-schema` according to D6.
   - A `start` with an eligible corrupt state validates the request against a `null` prior state. It retains the prior evidence directory contents because the old state's references cannot be resolved reliably. Other recorded writes sweep leftover `review-run-state.json.tmp-<pid>-<hex>` regular files under the lock, excluding recorded evidence by device and inode. An unresolved prior evidence target skips the sweep unless it is missing.
   - Serialize the new state canonically. Create the temporary file exclusively, write it and `fsync` it. Check that the lock still contains this writer's token. When recovering a corrupt state, claim an unused `review-run-state.json.corrupt-<YYYYMMDDTHHMMSSZ>-<hex8>` hard link to the original. Try at most eight names, retrying only name collisions. Then recheck the token. A missing or mismatched lock returns `busy` and removes the writer's temporary file.
   - Rename the temporary file over the state path, `fsync` the directory, and remove the lock only while it still carries this writer's token. A recovered write reports the backup's basename as `detail.moved_aside`. If publication fails, attempt to remove the backup only if it still names the same inode as the state path. Return `unwritable` with the backup basename if the backup could not be removed. If the lock was taken after commit, add `lock no longer held by this writer` to the warnings.
4. **Commit point and cleanup:** The rename is the commit point. Before commit, cleanup attempts to remove this writer's temporary file. It attempts to remove the lock when the token still matches. If initializing a newly created lock fails, the helper attempts to remove that lock. A failure in the leftover temporary-file sweep or after the rename (syncing the directory or removing the lock) still reports `recorded` with `detail.warnings`. Git bindings are sampled after acquiring the lock; the tree is resolved from the captured commit SHA rather than a second moving `HEAD` read.

The token check and state rename are separate operations. When two reclaimers race over a stale lock, one can displace a new writer's lock after its token check. Another writer can acquire the lock and proceed against the previous state before the rename.

## D4. Replay

Every record carries a caller-stable ID (`run_id`, `pass_id`, `correction_id`, `gate_id`, `audit_id`, `checkpoint_id`; a run has one `finish`). The same ID with identical caller input returns `replayed` (exit 0, no write); the same ID with different caller input returns `conflict` (exit 1). Replay compares stored caller fields (`C` in D6) against the canonicalized new input; helper-stamped fields (`H` and `G` in D6: helper times, Git-stamped heads and trees) are excluded while caller-observed times are compared (an omitted `started_at` or `completed_at` takes the helper's time on first record and matches the stored value on replay, while explicit values are still compared). `conflict` reports the first differing JSON path with stored and sent values cut to 80 characters. `recorded` and `replayed` both return helper-stamped `head`, `tree`, and `recorded_at` in `detail`; a replayed `finish` whose stored head differs from current `HEAD` adds `detail.head_moved: true`.

- **Check order:** (1) arguments and input shape, (2) replay lookup (an identical earlier record is `replayed` in any lifecycle state, including while paused or after finish; for `start`, the same `run_id` with identical input is `replayed` in any later state, different input is `conflict`, and a different `run_id` is refused `exists`), (3) lifecycle state (`not-started`, `paused`, `finished`), (4) environment validation (Git objects exist, evidence files exist inside `--dir` with matching digests).
- **Immutable pass, correction, gate, and audit records:** Passes follow the workflow-metrics state model (`bin/lib/workflow_metrics.py`): `record pass` with `state` `started` (replay key `pass_id + state`), `attempt` (`pass_id + voice_id + attempt_id`), `voice-complete` (`pass_id + voice_id`), and `completed` (`pass_id + state`). Later finding adjudication or resolution is recorded via `record correction` (`correction` extends the card's `pass|gate|audit` record types and never sets `adjudication: "duplicate"`). Gates and audits are append-only; for derivation, the last record in array order per gate or audit `name` is current.

## D5. Lifecycle

```text
  (absent) --start--> OPEN (segment 1)
  OPEN   --record / checkpoint (any kind but pause or resume)--> OPEN
  OPEN   --checkpoint pause--> PAUSED        (ends the segment)
  OPEN   --checkpoint resume--> OPEN         (closes previous segment as "interrupted" at its last helper-stamped write; opens segment n+1; refuses same non-null session_id)
  PAUSED --checkpoint resume--> OPEN         (segment n+1; takes its telemetry session id)
  OPEN   --finish prepared|stopped|blocked|needs-context--> FINISHED
  PAUSED --record / finish / other checkpoint--> refused "paused"
  FINISHED --any write but an identical finish--> refused "finished"
  (absent) --record / checkpoint / finish--> refused "not-started"
  any state --start, same run_id, identical input--> replayed (no write)
  any state --start, same run_id, different input--> conflict
  any state --start, different run_id--> refused "exists"
  any state --any record, checkpoint or finish identical to an earlier one--> replayed (checked before lifecycle)
```

Checkpoint `kind` is a closed v1 enum: `before-fix`, `next-cycle`, `stop`, `pause`, `resume`, `external-gate`, `ready`. Only `pause` and `resume` transition the lifecycle (`resume` on an `OPEN` run closes the interrupted segment at its last helper-stamped write and opens segment `n+1`, refusing `same-session-resume` when a non-null `session_id` matches the open segment's); the others are stored and `external-gate` and `ready` feed rendering. A pass is open from `started` to `completed`: an `attempt` or `voice-complete` for an unknown or closed pass is refused `invalid-input`; a new attempt on a voice already closed by `voice-complete` is also refused (an identical retry still replays), and `finish` with `outcome: "prepared"` while any pass is open is refused `invalid-input` (`stopped`, `blocked`, or `needs-context` may leave a pass open).

- **Compatibility:** Reading a stored state checks keys, types, and internal references only. Additive `v1` fields introduced after v0.86.0 (`writer` and `host` at root, and `segment` on `passes[]`, `corrections[]`, `gates[]`, `audits[]`, and `checkpoints[]`) are optional on read and default to `null` when absent so a v0.86.0 or pre-88A state file reads cleanly (`writer` is stamped on the next write, while a `null` `host` or `segment` on existing records stays `null`). An older helper that predates `host` reads a state carrying `host` from a newer writer as `newer-schema`. A state file with `schema: "review-run-state/v<N>"` where `N > 1`, or a `review-run-state/v1` file that fails validation whose `writer` is a valid 3- or 4-part numeric version string strictly newer than `helper_version` (padded 4-tuple comparison), is rejected as `unreadable` with reason `newer-schema` (exit 1); an unknown, missing, or mistyped field with an equal, older, `null`, or malformed `writer` is `unreadable` with reason `corrupt`. For a state that fails validation with a non-null writer, an unavailable helper version, a malformed version or an unsafe version component leaves ordering unknown. The result is `corrupt` and `start` preserves the file in place. A null or absent writer needs no comparison, including when the state JSON cannot be parsed.
An older helper that does not recognize `segments.end: "interrupted"` reports `newer-schema` when the stored writer is newer; the current helper accepts that end value. `show.writer` is the stored writer and `show.helper_version` is the executing helper version, or `null` when unavailable.

- **Derived segment identity and UUIDv5 namespace (`NAMESPACE`):** `export` and `derive` share the fixed UUIDv5 namespace `9aa572eb-215f-452f-99e8-2bfdf0329cf3` (`src/review-state/export.ts`, `bin/lib/workflow_metrics.py`). When `segments[i].session_id` is `null` (a segment whose telemetry start could not run), its derived session ID is `"extend-" + uuidv5(NAMESPACE, "<run_id>:segment:<n>")`, and every exported `event_id` and `run_step_id` is derived deterministically from `NAMESPACE` and `<run_id>:...`.
- **Write-once baseline records:** `cycle-1-baseline.json` and `cycle-1-fix-review.json` stay with the skill's existing write-once fence (`skills/review-and-prep.md`, `### Record cycle 1's full-review baseline`), whose checks now run in `bin/review-state full-review-record` (`src/review-state/fence.ts`); the state references them in `evidence` by relative path and `sha256` and never rewrites them.

## D7. Validation rules

In new input, unknown keys, missing required keys, wrong types, and out-of-enum values are refused (`invalid-input`) with the JSON path; omitted optional keys take their D13 default. Identifiers use the workflow-metrics grammar (`SAFE_ID_RE`, `VOICE_RE`, `PART_RE`, `DELEGATE_LABEL_RE`, `UUID_RE`); input `findings[].severity_source` also accepts upstream's `CRITICAL` and `INFORMATIONAL`, stored as `critical` and `info` while stored states keep the strict enum; SHAs are 40 or 64 lowercase hex; timestamps are UTC ISO 8601 ending in `Z`; strings have length bounds and forbid control characters (`\u0000`–`\u001f`, `\u007f`); URLs (`run.pr.url`, `details.run`) require `https://` or `http://` with no whitespace, userinfo, or query string, while `full_review_evidence.source` accepts any whitespace-free URI or resource reference (`1..500` chars, no control chars or userinfo); `evidence` paths are relative, resolve inside `--dir`, and name regular files matching `sha256` (if a named evidence file's resolved path, device and inode, size, or mtime changes between hashing and acquiring the lock, the command is refused `invalid-input` with rule `evidence-changed`); new evidence paths and resolved targets using helper temporary-file names are refused with rule `evidence-reserved-path`; the same checks cover `pregate.details.record_path`/`record_sha256` and documentation `details.section_path`/`section_sha256`. Cross-field rules: metrics v2/v3 rules for attempts, delegates (`credited` iff `completed` and `fallback_reason: null`; `fell-back` iff `failed` and `fallback_reason` set; `wall_ms`, `input_tokens`, `output_tokens`, `cache_read_input_tokens`, and `cache_creation_input_tokens` are integers `>=0` or `null`; ## D8. Commands, result envelope, and reason codes

`full-review-record WORKSPACE DIR write|check KIND FILE|BOUNDARY` is the
baseline fence used by `/review-and-prep` with or without `run-state=record`.
Before its first use, the skill checks that the launcher is executable and
that `full-review-record --help` succeeds. If the install root or launcher is
unavailable, or the help command fails, the skill skips the record checkpoints
and reports `record-missing` at the cycle-cap stop. The fence takes no lock and
prints a `FULL_REVIEW_RECORD:` line with exit codes `0`–`3`. It reads
`REVIEW_STATE_DIR/review-run-state.json` through `validateStoredState` only on
a `cycle-1-baseline` write with that variable set. Run
`bin/review-state full-review-record --help` for usage, messages, and exit codes.

D1–D3 and the JSON result envelope below describe the run-state commands.

Run-state commands: `build <command> --dir DIR [flags]` (builds the canonical JSON request from flags and files inside `--dir` as `request-<command-with-dashes>-<sha256-16>.json`, mode `0600`, reusing an identical file on rerun, and records it in the same call; `build --help` prints flag tables for all seven write commands and all four `record pass` states), `start`, `record pass|correction|gate|audit`, `checkpoint`, `finish` (each requiring `--dir DIR --input FILE`), `show --dir DIR [--base SHA] [--wtree TOKEN]` (read-only and lock-free; validates `--dir`, `review-run-state.json`, `host`, `run.repo` and `run.branch`, plus optional `--base` as an existing 40-hex commit and `--wtree` against `WTREE_RE`, returning the standard refusal/unreadable/usage envelope on error and printing one `"schema": "review-state-show/v1"` JSON line `{schema, state_path, rev, writer, helper_version, lifecycle, exit, run, binding, head, plan, policy, continuation, segments, checkpoints, last_checkpoint, passes, gates, audits, unresolved, finish, rendered}` on exit 0), `render --dir DIR --input FILE` (read-only on the state and lock-free like `export`, creating `full-receipt-<n>.md`, `comment-<receipt|paused|stopped>-<n>.md`, `pr-body-<n>.md` or `final-<n>.md` exclusively with mode `0600` in `--dir` and re-reading the bytes; success prints one `review-state-render/v1` JSON line `{schema, output, exit, files: [{path, display, sha256, bytes, chars}]}` on exit 0; refusals use the standard envelope with `invalid-input` rules — `not-renderable`, `stale-ready`, `greptile-gate-missing`, `skipped-pregate-lanes-too-long`, `receipt-mismatch`, `conflicts-with-state`, `forbidden-for-exit`, and the evidence-file rules — or `unwritable`), `export --dir DIR` (takes no `--input` and acquires no lock; validates `--dir`, `review-run-state.json`, `host` and `run.repo` while accepting a different `run.branch`, returning the standard refusal/unreadable envelope on error and printing one `"schema": "review-state-export/v1"` JSON line `{schema, run, segments, skipped, records, stage_runs}` on exit 0), plus `--version` (prints `review-state <version or unknown>` on stdout and exits 0), `--help`, and `<command> --help` (prints one `Example:` JSON line per request or render shape, and one example command in `show --help` and `export --help`). Every non-help, non-version write invocation (and every `show`, `export`, or `render` refusal) prints one JSON line on stdout (`{"v":1,"command","status","reason","detail","fix","state_path","rev","helper_version","side_effects","retry","retry_after_ms"}`), where `helper_version` is the checkout's `VERSION` string (or `null`), `side_effects` is `"committed"` for `recorded` and `"none"` otherwise, `retry` is `"no" | "same-input" | "after-fix" | "never"`, and `retry_after_ms` is `lockWaitMs` for `busy` and `null` otherwise. Non-successes write `ERROR <CODE>: <what>` and `FIX: <fix>` on stderr. An `internal-error` can add up to three stack frames when available. Its trace file is written only after `--dir` has been validated. If there is no trace, `detail.trace` is `null`. `build` adds `detail.overrides`, `[{flag, sent, used, rule}]`, to a result when it overrode a flag, prints one `WARNING BUILD_OVERRIDE:` line per entry on stderr, and appends `build-overrides.jsonl` in `--dir`; it adds `detail.derived`, `[{flag, used, rule}]`, when it filled in a value the caller left out from its read-only state lookup (only `--selected-attempt-id` today), with no stderr line or log entry. Other diagnostic values echoed in `detail` are truncated to 80 characters; `detail.overrides` retains the full caller values. Launcher: a POSIX shell guard (`command -v bun`, `printf`) that emits one `internal-error` (`cause: "runtime-missing"`) JSON line on stdout and `ERROR INTERNAL_ERROR:` / `FIX:` on stderr with exit 5 when Bun is missing, followed by `exec bun --no-env-file --no-install --config=/dev/null` (`bin/outside-review` pattern).

## D11. Relation to upstream and alternatives considered

The run state is internal to one `/review-and-prep` invocation and is not a portable evidence envelope (efficiency item E10 forbids another envelope format; [`docs/designs/review-evidence-envelope.md`](review-evidence-envelope.md) remains the portable reference). It does not extend upstream's `gstack-review-log` (which binds a single `/review` pass): the caller passes upstream's `wtree` token (`gstack-wtree --review`) as input, and `bin/review-state` imports nothing from upstream, so `bin/upstream-check` gains no entry.

- **Alternatives considered and not built here:** (1) read-only `show` is implemented in Track 79A part 1 (`src/review-state/show.ts`), while a separate `next` subcommand is not built because `show` plus [`docs/review-run-state-calls.md`](../review-run-state-calls.md) (`## Resume`) give the skill the checkpoint, `head` relation, and gate freshness directly without putting workflow decisions inside the helper (`CLAUDE.md` helper boundary); (2) `flock` process locks (absent from Bun `node:fs`; FFI is platform-specific); (3) batching existing inline writes or trimming instructions without a state (fails to recover records lost in a sandboxed first segment); (4) per-record `link()` claim files without a state file (cannot enforce `finish`, segment transitions, and run-wide ordering in one consistent document); (5) a Python helper alongside `workflow_metrics.py` (rejected for this Track because the card places the helper in `src/review-state/` and Tracks 78A/79A import its TypeScript reader). Exclusive lock and atomic write helpers are implemented directly in `src/review-state/store.ts` without importing private merge-gate helpers.

**Building requests (`bin/review-state build <command> --dir DIR [flags]`):** For the seven state-writing commands (`start`, `record pass`, `record correction`, `record gate`, `record audit`, `checkpoint`, `finish`), `build` maps fact flags and relative files in `--dir` to the request shapes in the table above in deterministic table-key order, writes `<dir>/request-<command-with-dashes>-<first 16 hex of SHA-256>.json` (`0600`, reusing an existing identical file on rerun), and records it in one call (`render` inputs stay `--input FILE`). `build` also accepts `--dir DIR` between `record` and its subtype (`build record --dir DIR <subtype> …`) and builds the same request. Derivations are mechanical only: `--delegation-line` is parsed by `parseDelegationLine` (the exact inverse of `renderDelegationPolicyLine`), `--prior-stops` defaults to `0`, `started` and `completed` omit timestamps and `candidate.tree`, `--delegate-file` with `--part` reads the `review-delegate run` output in `--dir` and copies the matching `parts[]` entry while deriving `outcome` (`credited` → `completed`, `fell-back` → `failed`) and string `dispatched_at`/`returned_at` when omitted, `findings` is written only when `outcome === "completed"` (default `[]`, dropping `--finding` on other outcomes with an override warning, rule `null-when-outcome-not-completed`) with `adjudication: "unclassified"`, `resolution: "open"`, and `severity_rubric` from `rubricForPart(--part)` (`core` → `core`; `specialist:*` and `red-team` → `specialist`; `native-adversarial` → `adversarial`; `greptile` → `greptile`; `qa`, `outside:challenge`, and `outside:structured` → `other`; no `--part` → `unknown`), `record correction` writes `resolution: "unknown"` when `--adjudication` is `rejected` (overriding any other `--resolution` with `unknown-when-rejected`), `record audit` with `--name coverage` writes `details.threshold: "n/a"` when `--coverage-threshold` is omitted with `details.pct` `null` (R1) and moves an over-64-character non-numeric `--coverage-threshold` into `result` as `"<result> — <text>"` with `details.threshold: "see result"` and overrides on `--coverage-threshold` and `--result` under rule `threshold-explanation-in-result` when that composition satisfies `isStr(…, 1, 200)` (R2), and `--evidence`, `--pregate-record`, and `--section` hash files inside `--dir` with `checkDirFile`. A literal `null` reads silently as an omitted flag on the 25 nullable scalar rows whose validator refuses the text `"null"` (`'build literal-null flag list matches validator nullability and text-null refusal'` in `tests/review-state.test.ts`), while the 10 nullable rows whose validator accepts the text `"null"` (`--wtree` on `start`, `record pass` `started`, `record gate`, `record audit`, `checkpoint`, and `finish`; `--gh-login` and `--policy-value` on `start`; `--reason` on `record gate`; `--stop-reason` on `finish`) keep `"null"` as text. When a `record pass` (`voice-complete`) call sends neither `--selected-attempt-id` (omitted or literal `null`) nor `--not-applicable` and the voice has exactly one completed attempt in the read-only state lookup, `build` fills in `selected_attempt_id` and reports `{flag: "--selected-attempt-id", used, rule: "only-completed-attempt-on-voice"}` in `detail.derived`; zero or several completed attempts, or unreadable state, leave the key omitted so the recorder refuses.

An omitted resolution on a rejecting correction stays omitted when a read-only lookup of validated run state shows that the finding's effective resolution is already `unknown`. For an existing correction ID, the lookup preserves its recorded resolution shape instead, including a legacy `null` resolution, so retries keep their original request bytes even after later corrections. Otherwise `build` derives `unknown`; explicit `--resolution unknown` still writes `unknown`, while a contradicting flag uses the same request shape as omission (override `used: null` when omitted). The recorder validates the final request under its state lock. Missing, unreadable or corrupt state is never repaired by the lookup.

The same read-only lookup sets `supersedes` on `record correction`: a new correction names the target finding's latest earlier correction, and the first correction on that finding omits the key (stored as `null`). An existing correction ID keeps its recorded `supersedes` value so retries keep their original request bytes even after later corrections. A contradicting `--supersedes` is replaced with an override (rule `latest-correction-on-finding`, with `used: null` when omitted). When the state file is missing, unreadable or invalid, or the target finding is absent from state, `build` passes `--supersedes` through unchanged and the recorder decides.
