# `/review-and-prep` run-state caller procedure

## Status

The caller records its run state by default; `bin/review-state` and `review-run-state/v1` stay experimental and internal ([design D1](designs/review-run-state.md#d1-roles)). Read this document at Step 1 except **Inline outputs**, which is read by heading when an output is written inline. Receipts, PR text and handoff lines are rendered with `bin/review-state render` from the recorded state, and render refusals follow **Degraded path (design D1)**. Upstream `/review` is wrapped, never edited. The state file is internal: external readers keep reading the published receipts and handoff lines, never `review-run-state.json`.

## Activation

Active by default when (1) the skill preamble printed an `EXTEND_ROOT:` line, (2) `"<extend-root>/bin/review-state" --version` exits 0 (`src/review-state/cli.ts` prints `review-state <version|unknown>` and exits 0), using the skill's single `<extend-root>` definition after its preamble, and (3) `<extend-root>/docs/review-run-state-calls.md` is readable. A policy line carrying `run-state=record` behaves exactly as one without it. When the root check or `"<extend-root>/bin/review-state" --version` fails, the full receipt says `Run state: unavailable (helper-missing)` and `Workflow metrics (local, optional): capture=unavailable (run-state unavailable: helper-missing).`; when this calls document is missing or unreadable, the skill's policy bullet records `Run state: unavailable (calls-document-missing)` and `Workflow metrics (local, optional): capture=unavailable (run-state unavailable: calls-document-missing).`. In both unavailable cases the invocation writes no run, pass or correction metrics records and writes each output inline from the skill's templates (and **Inline outputs** when this document is readable). Use the skill's baseline fence availability check and run an available fence without `REVIEW_STATE_DIR`.

## Directory, inputs and IDs

`--dir` is the invocation's evidence directory (**Evidence directory** in Step 1), which Step 1 creates with `mkdir -p` before `start` whatever the `run-state` value (the helper never creates it, [design D2](designs/review-run-state.md#d2-location)). Every state call is `"<extend-root>/bin/review-state" build <command> --dir <evidence directory> <flags>`; never write a request file by hand. Flags per command and `record pass` `--state`: `"<extend-root>/bin/review-state" build --help` and [design D13](designs/review-run-state.md#d13-request-shapes-and-walkthrough). Omit an optional flag to send no value. When a scalar flag maps to a nullable field whose validator rejects the text `null`, `build` also treats a literal `null` (as printed by `jq -r`) as omission without an override warning. This covers eligible ID, commit, timestamp, enum, URL, session ID, part and count flags. The flags `--wtree`, `--gh-login`, `--policy-value`, `--reason` and `--stop-reason` keep `null` as text. Omit them to leave them unset. Every file a flag names (`--evidence`, `--pregate-record`, `--section`, `--delegate-file`) is a path relative to `--dir` that resolves inside `--dir`, and the helper hashes or reads it directly. Save each `review-delegate run` stdout line as a file inside `--dir` and pass its relative filename with `--delegate-file`. IDs (`run_id`, `pass_id`, `attempt_id`, `correction_id`, `gate_id`, `audit_id`, `checkpoint_id`) are minted as the Workflow metrics section mints IDs today (fresh lowercase random UUIDs); voice IDs and `found_by` follow its attribution bullets (`skills/review-and-prep.md`). Every `record` call names its subtype (`record pass`, `record correction`, `record gate` or `record audit`); a bare `record` with no subtype is refused with `usage`. `build` also accepts `--dir <evidence directory>` between `record` and its subtype and builds the same request. Issue calls one at a time from this session, from inside the work tree.

`start` takes `--run-id`, `--base`, `--plan-ref`, `--plan-sha256`, `--policy-source` (the receipt's `Review policy source:` value: `"caller prompt"` for a policy line in the invocation prompt, `"user decision"`, or `"none supplied"` — never `"invocation prompt"`), `--max-continuations`, and optional `--policy-value` (absent stores `null`), `--delegation-line` (the receipt's exact `delegation: active (parts=…; config=…[; tools=…])` or `delegation: inactive — <reason>` line from **Delegate named specialist parts**, parsed by the helper as the inverse of its renderer; omit when the policy has no `delegate=` value), `--prior-stops` (defaults to `0` on an initial invocation; on a `/review-and-prep continue` invocation, pass `k >= 1`, the live count of distinct corroborated stopped-record SHAs on the PR), `--continues` (absent stores `null` when `--prior-stops` is `0`; required 40-hex commit SHA from the newest corroborated stopped record's `Stopped at: <full HEAD SHA>` line when `--prior-stops` is `>= 1`), `--wtree`, `--gh-login`, `--session-id`, and the PR flags (`--pr-url`, `--pr-repo`, `--pr-number`, `--pr-head-repo`, `--pr-head-branch`, `--pr-base-ref` when the PR is already known). The helper stores each `delegate=` part name as its part label (`specialist:<name>` for `testing`, `maintainability`, `performance` and `simplification`, `native-adversarial` for `adversarial`, and `red-team` for `red-team`), stores any other part label (`PART_RE`) as sent, and refuses anything else with `invalid-input` at `policy.delegation.parts` or `policy.delegation.tools`. A delegated attempt's `part` and each finding's `found_by` always use the part labels, never the `delegate=` names.

`record pass` takes `--pass-id` and `--state started|attempt|voice-complete|completed`:
- `--state started`: `--scope` (`local` or `greptile`), `--cycle`, `--coverage` (`full` or `delta`), optional `--delta-from` (required 40-hex when `delta`), `--commit`, optional `--base` and `--wtree`, and repeated `--voice <voice_id>`. `build` accepts no timestamp or tree flag; the helper stamps `started_at` from its UTC clock and resolves `candidate.tree` from `--commit`.
- `--state attempt`: `--voice-id`, `--attempt-id`, optional `--part <part-label>`, optional `--predecessor-attempt-id`, optional `--delegate-file <relative path in --dir>` (with `--part`), optional `--outcome`, optional `--dispatched-at` and `--returned-at`, and repeated `--finding <finding_id>,<severity_source>,<part>[,<part>...]` (or `<finding_id>,<severity_source>,attribution=<reason>` when `found_by` is empty). With `--delegate-file`, the helper reads the saved `review-delegate run` output from `--dir`, selects the single `parts[]` entry matching `--part`, copies it into the request (keeping `call_id` and any `null` `wall_ms` or token counts as explicit unknowns, rendered `unknown` in `Delegated part:` and derived as `null`, never `0`), derives `outcome` when `--outcome` is omitted (`credited` → `completed`, `fell-back` → `failed`), and copies string `dispatched_at` and `returned_at` from the entry when those flags are omitted. The helper writes `findings` only when `outcome` is `completed` (defaulting to `[]` when no `--finding` is passed and dropping `--finding` on a non-`completed` attempt with an override warning, rule `null-when-outcome-not-completed`). For each `--finding`, the helper sets `adjudication: "unclassified"` and `resolution: "open"` (never `"pending"`; triage's decision is a later `record correction`), accepts `severity_source` labels `P0`, `P1`, `P2`, `P3`, `critical`, `high`, `medium`, `low`, `info`, and `unknown` in any ASCII letter case and stores their canonical spelling (including `INFORMATIONAL` in any ASCII letter case as `info`; other spellings and padding are refused), and derives `severity_rubric` from `--part` (`core` → `core`; `specialist:*` and `red-team` → `specialist`; `native-adversarial` → `adversarial`; `greptile` → `greptile`; `qa`, `outside:challenge` and `outside:structured` → `other`; no `--part` → `unknown`). A `finding_id` names one finding for the whole run and is unique within one attempt: repeating an ID within one attempt's `--finding` list is refused (`duplicate-value`, `unique-within-attempt`), while the same ID on another voice's attempt, a later attempt or a later pass records as another report of that finding, so each voice records its own `--finding`. Never reuse an ID for a different finding: the helper cannot tell a reused ID from a repeat report.
- `--state voice-complete`: `--voice-id` and exactly one of `--selected-attempt-id` (the completed attempt the voice's result comes from) or `--not-applicable` (`not-applicable` or `user-deferred`). When the voice has exactly one completed attempt, `build` fills it in if both are left out (`--selected-attempt-id null` counts as left out) and reports it in `detail.derived`; with several completed attempts, name the one used. For no selected attempt, omit `--selected-attempt-id` and send `--not-applicable`; with zero or several completed attempts and neither flag, the call is refused (`exactly-one-of-selected_attempt_id-or-not_applicable`).
- `--state completed`: `--pass-id` and `--state completed` only (the helper stamps `completed_at`). Record it when the round closes even if a required voice has no selected attempt, for example when every attempt failed. Leave that voice unselected and finding cycles will report a partial observation. Never select a failed attempt or send `--not-applicable` to close such a voice.

Other commands:
- `record correction`: `--correction-id`, `--pass-id`, `--voice-id`, `--attempt-id`, `--finding-id`, and the changed `--adjudication`, `--resolution`, `--receipt-class` and `--fixed-in` flags. To update `Unresolved:`, find the latest pass whose selected attempts reported the finding. Target one of those reports. The receipt applies a valid correction on any of them to the whole finding. When triage reaffirms a receipt class after a finding is reported again, record it on a selected report in that pass.
  Correction validation and `--supersedes` use the exact report named by the target tuple. Omit `--supersedes` to use that report's latest earlier correction (none for its first correction). A contradicting `--supersedes` is replaced and reported as an override. To fix a previously rejected report, pass `--adjudication accepted` with `--resolution fixed`. With `--adjudication rejected`, omit `--resolution`: the helper writes `unknown`, and any other `--resolution` is replaced with `unknown` and reported as an override.
- `record gate`: `--gate-id`, `--name`, `--result`, optional `--reason`, `--commit`, optional `--base` and `--wtree`, repeated `--evidence <relative path>`, plus `--greptile-value` and optional `--greptile-run` for `greptile`, or `--pregate-raw-verdict`, `--pregate-wrapper-verdict`, `--pregate-policy`, `--pregate-record <relative path>` and repeated `--skipped-lane` (defaulting to none) for `pregate`. On a `probe-*` gate, `build` maps `reproduced` to `failed` and `inconclusive` to `blocked` with override rule `probe-outcome-to-gate-result`, and derives `--reason` from the probe outcome under the same rule when omitted. On `pregate`, `build` maps `narrowed` to `passed` with override rule `narrowed-pregate-recorded-as-passed` only when both verdicts are `pass` or `passed` (case-insensitive) and at least one `--skipped-lane` is supplied. Otherwise it refuses `--result` with `narrowed-requires-pass-verdicts-and-skipped-lane`. The stored skipped lanes distinguish a narrowed pregate from a full pregate.
- `record audit`: `--audit-id`, `--name` (`coverage` or `documentation`), `--result`, `--commit`, optional `--base` and `--wtree`, repeated `--evidence <relative path>`, plus optional `--coverage-pct` (number or `null`, default `null`) and optional `--coverage-threshold` for `coverage`, or `--report-id` and `--section <relative path>` for `documentation`. For `coverage`, `--coverage-threshold` is the threshold decision: the threshold percentage as a number or a label of at most 64 characters, never an explanation; it is required when `--coverage-pct` is a number and omitted when the audit has no percentage, in which case the helper writes `"n/a"`. A waiver, skip or other explanation goes in `--result` (at most 200 characters), the receipt's `<status or waiver>` slot: a skipped or not-applicable audit sends `--result "skipped — <reason>"` with neither coverage flag. When a non-numeric `--coverage-threshold` is longer than 64 characters and `<result> — <text>` fits within 200 characters, `build` moves the text into `result` as `<result> — <text>`, writes `"see result"` as the threshold, and reports both `--coverage-threshold` and `--result` as overrides with rule `threshold-explanation-in-result`.
- `checkpoint`: `--checkpoint-id`, `--kind`, optional `--base`, `--wtree`, `--session-id`, and repeated `--evidence <relative path>`.
- `finish`: `--outcome`, `--base`, optional `--stop-reason`, `--delta-base`, `--stop-count`, `--wtree`, `--review-restriction-resolved` (presence flag), `--readiness-confirmed-at`, repeated `--user-facing-change`, repeated `--evidence <relative path>`, and either `--full-review-commit`, `--full-review-tree` and `--full-review-source` (available) or `--full-review-unavailable <reason>` (unavailable).

When a flag contradicts a value the helper sets from another flag or the run state (for example `--resolution open` on a rejecting correction, `--supersedes` naming an earlier correction than the latest, `--delta-from` with `--coverage full`, or `--session-id` on a checkpoint other than `resume`), `build` uses the helper's value, prints one `WARNING BUILD_OVERRIDE:` line per such flag on stderr, lists it in the result's `detail.overrides`, appends it to `build-overrides.jsonl` in `--dir`, and still records; continue without a retry. Missing caller facts and flags that conflict where neither side is determined are still refused. Design D13's **Builder coverage of cross-field rules** lists every rule.

For compatibility with successful older requests, an omitted `--resolution` stays omitted when the targeted report's effective resolution is already `unknown`. A read-only lookup of the validated run state preserves that omission on new corrections and preserves each existing correction's recorded resolution shape on replay; otherwise the helper derives `unknown`. Explicit `--resolution unknown` still writes `unknown`; a contradicting resolution uses the same request shape as omission, with override `used: null` when the key stays omitted. The recorder remains authoritative under its state lock; the lookup never changes the validator, stored format or `--input` behavior.

## Fixed points

Use these calls to start recording and while recording remains active. After the **Degraded path** stops recording, skip `derive` for the rest of the invocation.

| Skill heading | Call | When |
|---|---|---|
| `## 1. Establish the branch, PR, and review inputs` | `start`, then `derive`, `record gate` (`greptile`) | Run `build start` once at the end of Step 1 when the base tip, plan reference and SHA-256, parsed policy (`--policy-value`, `--policy-source`, `--delegation-line`) and continuation counts (`--prior-stops`, `--max-continuations`, `--continues`) are known, and before Step 2's first span; set `--session-id` from this segment's `GE_TELEMETRY: session=…` line, or omit it when the start printed any `GE_TELEMETRY: unavailable` line or no session line; omit the `--pr-*` flags and `--gh-login` when not yet known. Then run `derive` (below) before any span. When Step 1 recorded a Greptile skip, run `record gate` named `greptile` after `start` and `derive`. Step 1's own `evidence` and `scope` spans come before `start` and are not emitted while the run state is recorded. |
| `## 4. Trigger once and await Greptile`, `### Greptile exits that need a user decision`, `### Readiness` | `record gate` (`greptile`) | Run `record gate` (`greptile`) each time the receipt's H-B Greptile value is decided or changes (Step 4's outcome, a recorded waiver, Step 6's changed applicability decision), with `--greptile-value` starting with one of the four published forms (`completed on <SHA>`, `unverified — no response after 10 minutes` with any E4 decision suffix, `skipped — <reason>`, `postponed — awaiting manual testing`; for a skip, `skipped — <reason>; do not run it`, as `B-GREPTILE-SKIPPED` in `tests/fixtures/handoffs/cases.json` shows) and `--greptile-run` the run link (omit when `null`); `render` keeps only the form's SHA, reason or decision reference and writes the rest from fixed text, and on a `greptile-value-unrecognized` refusal in an open segment, record the `greptile` gate again with a published form and render again instead of writing the line inline. See the manual testing row for a paused segment and **Resume** for a finished run; `--result` is `passed` for a completed run, `blocked` with `--reason unverified` for the no-response fallback, and `not-run` with `--reason` for a skip or postponement (the renderer reads only `details`); the candidate is the current `--commit` HEAD and `--base`. The last `greptile` record is current. |
| `## 2. Review and verify locally`, `### Scope a re-review to its delta`, `## 5. Triage, fix, and verify locally`, `## 4. Trigger once and await Greptile` | `record pass`, `record correction` | Record `pass` states for each review round (`started` before dispatch, each `attempt` and `voice-complete` as its result is consumed, and `completed` when the round closes; `scope` is sent on `started` only — `"local"`, or `"greptile"` for the Greptile pass — and `attempt`, `voice-complete` and `completed` carry none). Use `record correction` to update a report's adjudication, resolution or receipt class. Run `checkpoint before-fix` for cycle 1 after the fence's `cycle-1-baseline` write (once its `check` answers present) and before the first fix; later cycles run `checkpoint before-fix` before their first fix, and run `checkpoint next-cycle` at each later cycle's Step 3. |
| `### Prove /ship's release gates on this head`, `### Narrow the pregate after an accepted pass`, `### Repair a test-only final-gate failure` | `record gate`, `record audit` | Run `record gate` for `pregate` and `tests`; run `record audit` for `coverage` and `documentation`. End the segment as in **Segments**, follow **Resume** to open a new segment before recording the corrected gate, then checkpoint the pause again before rendering. |
| `### Greptile exits that need a user decision` | `checkpoint pause` | Run `checkpoint pause` (with the current base) at each deliberate pause that a later resume continues (manual testing, Greptile exit question, configuration pause). |
| `**Segments**` (`~/.gstack-extend/bin/preamble review-and-prep --resume`) | `checkpoint resume`, then `derive` | On a resume, follow **Resume** below. |
| `### When /review stops at its cycle cap` | `checkpoint stop`, `finish` (`stopped`), `render` (`full-receipt`, `comment`, `body`, `final`) | After the dedicated evidence comment and the policy decision, run `checkpoint stop`, `finish` `stopped` (`--outcome stopped --base <fetched base> --stop-reason review-cycle-cap --delta-base <Delta base SHA> --stop-count <k>`, optional `--wtree <token>` and `--review-restriction-resolved`, and either `--full-review-commit <full-review commit> --full-review-tree <its Git tree> --full-review-source <evidence comment permalink>` or `--full-review-unavailable <why>`), then render `full-receipt`, `comment` (post it), `body`, `final`. When the stop's policy line differs from the recorded `policy` value or source, write the full receipt, stopped comment and H-E prompt inline instead (the body and stage line may still render). |
| `### Report elapsed time and stop on provider failures` | `finish` (`blocked`), `render` (`full-receipt`, `body`, `final`) | Run `finish` `blocked` with `--stop-reason provider-failures`; with a draft, render `full-receipt` and `body` (`comment_url: null`); always render `final`. |
| `### Refresh a prepared PR after a base move` | `finish` (`escalated` or `blocked`), `derive`, `render` (`final`) | On a base-move refresh escalation, run `finish` `escalated` with `--base <last-merged-base>` and `--stop-reason` from the closed H-G escalation tokens (`reviewed-code-conflict`, `reviewed-behavior-change`, `delta-finding`, `delta-unverified`, `final-gate-failed`). For Section D's BLOCKED exits, run `finish` `blocked` with `--stop-reason merge-blocked` and the last committed merge's base, or the earlier receipt base before any merge commits. Then run `derive` and render `final`. The escalation uses `next: review-and-prep; status: stopped`. |
| `### Readiness` | `checkpoint ready`, `render` (`full-receipt`, `comment`, `body`, `final`), `finish` (`prepared`, `blocked`, `needs-context`), `derive` | Once every readiness gate passes, run `checkpoint ready` (fetched base, `wtree`); render `full-receipt`, then `comment`, post it with `--body-file`, render `body` with its permalink and splice that section into a fresh read of the PR body under the existing collision procedure; recheck, `gh pr ready`, readback; `finish` `prepared` with `--readiness-confirmed-at`, repeated `--user-facing-change`, and the `ready` checkpoint's `--base`, `--wtree` and `--review-restriction-resolved` when the comment set it, recording nothing between the comment render and `finish` except an `open-pass` recovery under **Degraded path**; `derive`; render `final` and end the message with that file's bytes after the model's own prose. A recheck failure returns to fixing, and a later pass records a new `ready`. Any other blocked or needs-context exit records `finish` with that outcome and renders `final` (its stage line); its body stays inline. |
| `### Telemetry finish` | `derive` | Run `derive` once more after the pause checkpoint or `finish` and before Telemetry finish. |

## Resume

- **Locating the run:** Use the evidence directory that is either the first segment of the corroborated paused/stopped comment's `Full receipt:` locator under the evidence root (**Evidence directory**; a legacy `~/` or absolute path names it directly), or the external-gate pause's `Evidence directory:` line. For an interruption without a pause, inspect the newest invocation directory under the evidence root (**Evidence directory**) whose state `show` binds to this repository and branch. A locator or path only locates: Step 1's author, edit-history, ancestry, PR identity and restriction checks still apply.
- **Reading the state:** Before scheduling any review or check, run `"<extend-root>/bin/review-state" show --dir <dir> --base <fetched base>` (plus `--wtree <token>` when known). Read that line for the recorded checkpoint, passes and gates instead of re-reading prior transcripts or rebuilding receipt records.
- **Mismatched state:** Any refusal (including `not-started`, `worktree-mismatch`, `corrupt` or `newer-schema`), a `last_checkpoint.head` different from the corroborated pause/external-gate/stop record's head, or a `rev` lower than the corroborated full receipt's `Run state: recorded (...; rev <n>)` line takes **Degraded path (design D1)** for the rest of this invocation. Never `start` a replacement run in that directory; never `start` a new run in that `--dir` or silently discard the recorded run. Continue inline under the skill's existing resume, scope and authorization rules; a state mismatch never clears a hold. `head.relation: "diverged"` also takes the degraded path and the skill's full-scope/ancestry rules.
- **Finished and open runs:** `lifecycle: "finished"` resumes nothing. Return to Step 1's existing finished/prepared, blocker-recovery or cycle-stop handling; an authorized new review or continuation uses a new run in a new `--dir`, never reopens the finished state. Resume an open run only when its previous session has ended, including when telemetry supplied a null session ID. A repeat inside the same live session continues its active segment without `checkpoint resume`; uncertain liveness does not authorize splitting another session. Determine this from the host's session state.
- **Escalated refresh:** On an ordinary invocation on a draft, include the newest matching invocation directory in the run lookup after local refresh escalation. Require the same repository, branch and PR, an ancestor `finish.head` and no superseding corroborated preparation. A corroborated `finish.outcome: "escalated"` routes to a fresh full review with a new run. With inline or missing state, the stale prepared-receipt rule in `resume-review-records` applies. An escalation clears no independent hold and adds no cycle-cap restriction.
- **Resuming:** Retain the inspection above, mint a new `checkpoint_id` and run `build checkpoint --kind resume` with `--checkpoint-id`, `--base <fetched base>`, `--wtree` (when known), and `--session-id` from this segment's telemetry `session_id` (omitted when `null`, as on `start`), then run `derive`. A trailing `resume` stamps the current head: `head.relation: "same"` against that stamp never proves earlier review coverage. Compare the relevant earlier checkpoint/pass candidate to the live content and apply the skill's ordinary freshness and full/delta selection rules. Delta bases are frozen candidate snapshots, never checkpoint HEADs.
- **Where to continue:** Use `last_checkpoint` (or the checkpoint before `resume` when the latest is already `resume`):

| Last checkpoint | Continue at |
|---|---|
| none | Finish open passes' open voices, then continue at the step after the last completed pass. Use the 113A recovery below only when cycle 1's baseline write point has not passed. |
| `before-fix` | That cycle's Step 5; inspect the work tree for partially applied fixes and retain their review obligations. Empty `unresolved` alone never proves readiness. |
| `next-cycle` | That cycle's Step 3, using the skill's full/delta selection and validated snapshot base. |
| `stop` | The cap stop's `finish` (`stopped`) and its renders, preserving the cycle-stop authorization and evidence requirements. |
| `pause` (without preceding `external-gate`) | Manual-testing / Greptile-exit / configuration resume; reuse `passes`, `gates`, and `audits` where `fresh: true` and `evidence_ok: true`. |
| `external-gate` + `pause` | **Resume entry** in **Pause for an external full-suite gate**, including its corroborated external checkpoint history and attestation checks; `show.checkpoints` is a summary, not a replacement for that evidence. |
| `resume` | Inspect the checkpoint immediately preceding the trailing `resume` checkpoint(s) and apply its row above. |
| `ready` | Readiness after `checkpoint ready`: re-establish `checkpoint ready` after `resume` before rendering or finishing. Reuse a listed rendered comment only when corroborated as posted for the same head and its evidence remains current under Readiness, including a `Greptile:` line matching the current renderer; a filename or hash alone grants no reuse. Otherwise render new output and follow the normal receipt/body, recheck, ready/readback and finish order, recording nothing between the new comment render and `finish` except an `open-pass` recovery under **Degraded path**. |

- **Before `before-fix` (the 113A failure mode):** When no `before-fix` checkpoint exists, live HEAD is the same as cycle 1's recorded candidate and its review collection evidence is available, the baseline write point has not passed. If `passes` already has cycle 1's completed voices, do not re-run those voices or ask for `continuation=full`; record any missing voice result or `probe-<id>` gate from that collection evidence, then rerun the fence's identical `cycle-1-baseline` write with `REVIEW_STATE_DIR=<dir>` (`provenance=write-point`). Never invent a missing result. The normal before-fix checkpoint follows; a changed candidate takes the skill's existing missed-record and review rules.
- **Reuse rules:** Reuse gate/audit evidence with `fresh: true` and `evidence_ok: true` under that gate's own result and authorization rules; everything else follows the skill's own invalidation rules. Greptile applicability and consumed-run/hold rules still come from Step 1/4/6's live corroboration, never a `not-run` result alone. Recorded passes, findings and corrections are never re-recorded, and existing rendered files are not rebuilt or overwritten. New output required by changed bindings follows the normal renderer/readiness rules. An `ahead` head does not itself authorize a delta: use the validated full/delta chain and snapshot procedure.

## Derive and spans

Run `"<extend-root>/bin/gstack-extend-telemetry" derive --dir <evidence directory>` from the work tree after `start` and each `checkpoint resume`, immediately before each receipt's `metrics read`, and after the pause checkpoint or `finish` and before Telemetry finish ([docs/telemetry.md](telemetry.md#review-state-derive), Review-state derive). It writes the run `begin`, `pass`, `correction` and run `end` records and any missing `stage-runs` rows; the model writes none of those. In the call that runs the first derive of a segment, resolve `GX_LIB` with the Workflow metrics section's resolver snippet; set `GX_RUN` from `data.current.run_step_id`, `GX_SID` from `data.current.session_id`, and `GX_CAPTURE=1` only when `data.current.run_begin` is `recorded` or `replayed`. Spans, waits and decisions stay as the Workflow metrics section says, with no context-override argument; fix-cycle corrections and attempt `model_context` are not derived (accepted measurement difference, decision d8). Workflow metrics count each selected report separately, including reports that share a `finding_id`. Each receipt's `metrics read` uses `data.current.session_id`. When derive supplies no session ID, skip the read and report the capture status with the actual reason. Report explicit non-`ok` results other than `usage` with their actual reason in chat. Set `GX_CAPTURE=0` and skip spans and raw decisions when no binding is available. A later derive recovers a missed write. When `"<extend-root>/bin/gstack-extend-telemetry" derive --dir <evidence directory>` prints no parseable result line or a `usage` result (possible version skew), or an `ok` or `partial` result lacks the `data.current` binding fields above, keep recording and rendering, write no metrics records, leave spans unavailable (`GX_CAPTURE=0`), and add `Workflow metrics (local, optional): capture=unavailable (derive-missing).` to the full receipt if this reason still holds at receipt time. The run-state unavailable line below takes precedence if recording later stops. A successful later `derive` in the same checkout writes the records from the retained state.

## The baseline fence

While the state is being recorded, run the `cycle-1-baseline` fence with `REVIEW_STATE_DIR` set to the evidence directory for that call only. Cycle 1's local `started` record and its `probe-<id>` gates must carry `candidate.commit` B (the HEAD cycle 1 reviews), never the snapshot S, because the fence's precheck matches `probe-<id>` gates to cycle 1's pass by `candidate.commit`. On `refused cycle-1-baseline: write point not reached (<id>)`, record the named voice result or `probe-<id>` gate and rerun the identical write; never write the baseline around it. `FULL_REVIEW_RECORD: refused cycle-1-baseline: write point not reached (run-state unreadable)` means the fence could not read or validate `review-run-state.json` (`runFullReviewRecord` precheck in `src/review-state/fence.ts`); take the **Degraded path** with reason `fence-run-state-unreadable` and rerun the identical write once without `REVIEW_STATE_DIR`. `FULL_REVIEW_RECORD: refused cycle-1-baseline: write point not reached (cycle-1-pass)` means the state holds no local, full-coverage cycle 1 pass, which only happens when that pass's `started` record was never sent or was sent with another scope, cycle or coverage (a refused call has already stopped recording); never record a replacement pass after the fact, take the **Degraded path** with reason `fence-cycle-1-pass-missing` and rerun the identical write once without `REVIEW_STATE_DIR`. Neither recovery repairs, moves aside or restarts the state (`start`'s move-aside is not a resume step, **Resume**), and the write keeps `provenance=write-point`. Once the state is unavailable for the rest of the invocation, run the fence without `REVIEW_STATE_DIR` so a degraded run never blocks its own `cycle-1-baseline` write.

## Degraded path (design D1)

When `finish` refuses with violation rule `open-pass`, recover from the refusal before taking the degraded path. For each entry in `detail.open_passes`, record any voice result the run has and close the pass with `record pass --pass-id <id> --state completed`. Leave voices whose attempts all failed unselected. This recovery is the sole recording exception between the comment render and `finish`. Closing a pass preserves the review content of the prepared receipt and comment. If recording a missing voice result changes that content, follow **Receipts and handoffs** to render the accurate output. Rerun the identical `finish` once. If it is still refused, take the degraded path below.

On a helper result with `retry: "same-input"` (`busy` or `unwritable`; wait `retry_after_ms` when present) or no parseable result line, rerun the identical command once. If it still fails, or on `bad-dir`, `unreadable` (`corrupt` or `newer-schema`), a `usage` refusal for a command or flag this procedure names (version skew: an installed helper older than the skill) or any other refusal, record no further state for the rest of the invocation, set `GX_CAPTURE=0` and skip raw decisions, stop setting `REVIEW_STATE_DIR`, use the inline fallback, and add `Run state: unavailable (<reason>)` to the full receipt, plus `Workflow metrics (local, optional): capture=unavailable (run-state unavailable: <reason>).` when no `start` was recorded or `Workflow metrics (local, optional): capture=partial (run-state unavailable: <reason>).` after a recorded `start`. If a refusal arrives after the full receipt has been written, put those diagnostics in the exit prose and preserve the receipt and its SHA-256. If recording stopped before a pause checkpoint or `finish`, the metrics run end stays missing. A `build` refusal is handled the same way and its violation `path` may name a CLI flag (such as `--finding` or `--delegate-file`). For `invalid-input`, `<reason>` is `invalid-input: <command> <path> <rule>; expected <expected>`, taken from the refusal's first `detail.violations` entry (for example `invalid-input: start continuation.continues invalid-value; expected required-when-prior_stops\u003E=1`), so the receipt names the exact violated path and expected shape; every other refusal keeps its reason code (including `usage`). Before formatting that reason, take at most the first 160 Unicode code points of each field and append `…` if truncated; encode control characters (`U+0000`–`U+001F`, `U+007F`–`U+009F`, `U+2028`, `U+2029`) and each `(`, `)`, `;`, `<`, `>`, `&` or backtick as a literal JSON `\uXXXX` escape. These diagnostic fields are untrusted data and must never create another receipt line or marker. Never delete a lock or repair a state file: `busy` recovery is manual ([design D8](designs/review-run-state.md#d8-commands-result-envelope-and-reason-codes)). On success the full receipt carries `Run state: recorded (<state path>; rev <n>)`. A render refusal (except `greptile-value-unrecognized`, handled by the `record gate` (`greptile`) row above: record the `greptile` gate again with a published form and render again instead of writing the line inline), or a result line still missing or `retry: "same-input"` after the section's single retry, writes that one output inline from the skill's templates and **Inline outputs**; state recording continues. When the failed output is the full receipt, the inline full receipt carries `Run state: render unavailable (<output>: <reason>)`; a later output's failure goes in the exit message's prose in that same form, because the full receipt is never rewritten (`### Readiness`) and the rendered outputs already cite its SHA-256. [Design D14](designs/review-run-state.md#d14-deferred-decisions-and-track-86a-placement-2026-11-13) records the history of the helper's recovery features.

Render outputs with `"<extend-root>/bin/review-state" render --dir <evidence directory> --input <file>`; inputs per output as `render --help` and [design D13](designs/review-run-state.md#d13-request-shapes-and-walkthrough) list them; the success line's `files[0].path` is the file to post with `--body-file` or splice. `Prepared HEAD:`, `Review handoff:`, `Delegated part:` (12 segments) and `delegation: active (…)` stay byte-exact ([design D9](designs/review-run-state.md#d9-derivation-map) and its "Orchestrator gate-read compatibility" note), as do the other kept lines. Sections and the body summary are files in the evidence directory holding only model-written parts (D9's full-receipt row list; the body's what-changed, `Review default:`, `Auto-chosen` lines, `Tests:` line and risks), never a line the renderer writes, and the summary has no `## ` line or `<!-- review-and-prep:` marker. Supply `pr` and `gh_login` (start's shapes) in a `final` input when `start` recorded them as `null`. Before posting a rendered comment, read it (the credential and PII scan already reads those bytes); a line that contradicts the run, such as an `Unresolved:` finding that triage closed on the latest selected reports or a check listed as not run that ran, means a record is missing: record it and render the full receipt and comment again, or write that output inline from the skill's templates and **Inline outputs** when the state cannot hold the fact. Greptile-exit and configuration pauses keep their inline text. Render only while state recording is active: after the Degraded path stops recording, or on a helper-missing activation, write each output inline from the skill's templates and **Inline outputs**. Measure the spliced body with Step 3's `PR_BODY_SIZE` check as today.

## Inline outputs

Read this section by heading when writing an output inline under the cases documented above. On the normal recorded path `bin/review-state render` implements these line-assembly and ordering rules directly (`src/review-state/render.ts`).

- **Compact receipt comment (`### Readiness`):** Use the compact receipt fence in `skills/review-and-prep.md` (`### Readiness`). `Delegated part:` appears once per delegated part for each review cycle that ran it, in cycle order, when `delegate=<part>` is active (a part run in three cycles has three lines, and its last line is its latest cycle), and `Unresolved:` records unresolved findings or `none recorded`; keep both in the compact receipt comment as machine-read lines in their exact grammar rather than moving them only to `full-receipt-<n>.md`. `reviewRestrictionResolved: true` appears only when the readiness rule requires it. Write each path under the evidence root as its evidence locator (**Evidence directory**), and any other path under `$HOME` as `~/…`.
- **PR body section (`### Readiness`):** The PR body's `## Review and prep` section carries only: the status line (`prepared`, `PAUSED — manual testing required`, `STOPPED — review cycle cap`, or `BLOCKED — provider failures`); what changed and why (two to four sentences); the `Review default:` line and every `Auto-chosen (veto by replying on this PR):` line verbatim at line start, plus other decisions open to veto; one `Tests:` line (suite result and selection, pregate verdict, Greptile state); risks and open checks (pending user checks on a pause); and `Receipt:` the receipt, paused or stopped comment permalink (none yet on a BLOCKED exit) and `Evidence:` the full receipt's evidence locator (`full-receipt-<n>.md`) and its SHA-256.
- **Paused comment (`### Manual testing checkpoint and resume`):** The paused comment uses Step 6's compact shape: mark it `<!-- review-and-prep:paused:<full-sha> -->`, include `Status: PAUSED — manual testing required`, `Prepared HEAD:` (the checkpoint), `Review policy:`, `Greptile:` (the postponed or skip value), every `Delegated part:` line and `Unresolved:` in their exact grammar, `reviewRestrictionResolved: true` when applicable, one line: `Resume with /review-and-prep resume; do not run /ship on this draft.`, and `Full receipt: <evidence locator>; sha256: <64 hex>`. The marker is distinct from `review-and-prep:receipt:`, so `/ship-and-land` never reads a paused receipt as prepared.
- **Stopped comment (`### When /review stops at its cycle cap`):** The stopped comment uses Step 6's compact shape: the `<!-- review-and-prep:stopped:<full-sha> -->` marker, `Status: STOPPED — review cycle cap`, the five stopped labels (`Stopped at:`, `Delta base:`, `Review policy:`, `Review policy source:`, `Full-review evidence:`), `Unresolved:`, `Continuation: <k> of <n>`, its one `Skipped pregate lanes:` or `Ship gates:` line, every `Delegated part:` line, `reviewRestrictionResolved: true` when applicable, and `Full receipt: <evidence locator>; sha256: <64 hex>`; the other listed lines live in `full-receipt-<n>.md`, and the dedicated full-review evidence comment procedure is unchanged.
- **Stage line and `User-facing change:` placement (`## 7. Emit the copyable prompt for a new session`):** The H-B prompt is `next: ship-and-land; status: done`, with `head` the Prepared HEAD and `plan-sha256` the prompt's `SHA-256`. A manual-testing pause prints `next: pair-review; status: paused` with `head` the checkpoint SHA; a cycle-cap stop prints `next: review-and-prep; status: stopped` with `head` the `Stopped at` SHA. A blocked or needs-context exit prints `next: none` and that status after its resume summary, with no fence. `plan-sha256` is `none` when the exit names no plan hash. When the prepared diff has user-facing changes, print one `User-facing change: <one plain sentence>` line for each change in the final message on a `next: ship-and-land` exit, outside the H-B `Run /ship-and-land` fence: place them after the fence's closing line and before the `Stage handoff: stage-handoff/v1;` line, which stays the last line of the message; see [release disclosures](workflow-handoffs.md#release-disclosures) (`docs/workflow-handoffs.md`). Never put `User-facing change:` on the `Run /ship-and-land for this prepared PR.` line, inside the H-B fence, or on the `Stage handoff: stage-handoff/v1;` line. Write one disclosure per line, label first, singular and inline. The lines are not added to the compact receipt comment, the PR body's `## Review and prep` section or the kept marker set. No manual testing pause, cycle stop, blocked result or external-gate exit prints them.
